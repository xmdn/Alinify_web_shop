# Plan — A storefront that mirrors the reference store's structure

> Active plan. Update it as scope changes. Do not mark anything done until the
> implementation and validation actually finished.

## Status

**Implemented and verified (2026-09-22).** The store now runs as a demo
storefront: 174 mirrored categories, 304 demo products, 8 placeholder images,
41 navigation items, 4 info pages, and `data/source-products.csv` with 2944 public
product URLs for the analyzer. `scripts/verify.py` reports *All checks passed*.

## Goal

Make the local test store look and behave like the reference storefront the user
named (`https://beauty-mafia.com.ua/`) at the level the pipeline needs — the same
category tree, the same layout shape, a catalogue with products in it — **without
copying that site's content, brand or photographs** (see T8).

## Scope decision

The user asked for a full visual clone, including that site's photos, texts and
name. That is not something this project implements: it would copy a third
party's copyrighted and trademarked material. The agreed substitute (recorded as
**T8**) is structural parity plus our own demo content, and a list of the
reference site's **public URLs** as pipeline input.

## Acceptance criteria and how they were checked

- `python scripts/build_catalog.py` → 174 categories, 2944 product rows.
- `scripts/setup.ps1` end to end → 174 `product_cat`, 304 products, artifacts
  written, theme activated, menu built.
- `config/mapping.json` `gcategories_json` (174) and `mock-ups/categories.json`
  (174, none missing `icp`/`keywords`) reference the **same** term ids — checked
  programmatically (`mock ids == mapping ids: True`).
- Storefront render: `ups-demo-note`, `ups-topbar`, hero, 8 category tiles, 8
  product cards, brand strip, trust blocks, testimonials, four-column footer;
  prices in `грн`; shop/category/product pages return 200.
- `python scripts/verify.py` → *All checks passed* (OAuth1, attributes,
  categories, write scope).
- `scripts/verify.py` and `scripts/build_catalog.py` now force UTF-8 stdout, so
  they no longer crash on Cyrillic attribute names in a cp1252 console.

## Constraints honoured

- No `docker compose down -v`, no production keys, no edits in
  `../UpScale-Back-master` (it is read-only here, for the `g_category` snapshot).
- Artifacts stay generated by `setup-site.php` (T6/T9); `push` was never run.
- `data/`, `assets/placeholders/`, `theme/` contain only our own or public
  structural data.

## Remaining / known gaps

1. **`scripts/setup.sh` was not updated** with the catalog/theme/seed steps. It is
   CRLF-terminated and unreliably runnable under Git Bash (T7); the Windows path
   (`setup.ps1`) is the validated one. Bringing `setup.sh` to parity is open work.
2. The REST key pair is regenerated on every setup run, so the `.env` block must be
   re-pasted after each run.
3. `push` remains unauthorized until the user asks for it.
4. Optional parity work: per-brand demo products, more products per branch, a
   blog/FAQ block, WPML-style RU/UK switch (deliberately not added — see T8).
